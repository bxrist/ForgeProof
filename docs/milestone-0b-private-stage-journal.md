# Milestone 0B — Private exact-stage journal (source only)

This standalone module supplies an experimental persistence boundary for the outputs of `sealed-core-stage`, `sealed-evidence-stage`, `sealed-email-stage` and `sealed-api-key-stage`. It changes no producer, importer, app entrypoint, auth, Stripe, SQL, webhook or package contract. It has no Git, network, append, delivery or production capability. Production export remains blocked. Milestone 0B remains **NO_GO**; every returned summary explicitly denies production GO and full application migration completion.

## Trusted inputs and exact bytes

`openPrivateStageJournal({directory, worktree, binding, journalKey, proofKey})` opens an already provisioned owner-only directory (mode 0700, owned by the process user). Supply absolute paths and an authenticated owner-workflow binding with exactly `{authenticated:true, tenantId, repositoryId}`. These are trusted operator inputs, never fields accepted from an unauthenticated request. The directory must be outside the supplied real worktree and any ancestor with a Git marker (`.git` file or directory containing HEAD). The helper does not discover every linked worktree, alternate object directory, backup location or future Git initialization: the operator must keep this directory outside **all** source trees, ledger/object storage, public Git, analytics and logging. It neither creates nor repairs directories or permissions.

Supply a fresh independent 32-byte Buffer `journalKey` from external private custody, distinct from all source, archive, mail, custody and signing keys. Supply a 32-byte `proofKey` matching the independently retained stage proof. Equality of these two supplied keys is rejected; independence from keys absent from this API remains an operator responsibility. No environment or secret files are read. Keys are copied in memory and copies cleared on close; JavaScript cannot guarantee erasure of all runtime copies.

Every call takes an independently retained expectation with exactly `{id, kind, sourceCommitment, stageDigest}`. IDs are operator-chosen safe opaque strings (1–128 alphanumeric, underscore or dash characters), stable across restart, and unique within the directory across all scopes and stage kinds. Do not embed customer identifiers. `kind` is `core`, `evidence`, `email` or `api-key`. The source commitment is the 64-character lowercase keyed commitment from the authenticated source verification, never a fresh hash of unauthenticated rows. `stageDigest` must be `hmac-sha256:` plus 64 lowercase hex characters.

| Producer | Bytes passed to persist | Proof key and digest |
| --- | --- | --- |
| Core | UTF-8 `JSON.stringify(output)` of the complete returned stage (including summary) | Core producer has no native stage digest. The trusted workflow must independently retain HMAC-SHA256 over these exact bytes using its source HMAC key. This is a new journal input convention, not an existing core proof. |
| Evidence | UTF-8 `JSON.stringify(output.privateStage)` | Existing `output.summary.stageDigest`, archive key |
| Email | UTF-8 `JSON.stringify(output.privateStage)` | Existing `output.summary.stageDigest`, mail key |
| API key | UTF-8 serialized `output.privateStage` | Existing `output.summary.stageDigest`, source HMAC key; producer digest uses `canonical(privateStage)` |

The journal accepts only Buffer bytes, bounds the stage to 32 MiB, checks JSON version/basic transaction-array structure, and checks embedded scope/source when provided. Core also requires its summary source and denial of production GO. It verifies the expected stage HMAC. It is **not** another schema/relation/receipt validator: the owner workflow must first run the existing authenticated sealed-source verification and producer. Evidence has no embedded scope/source; its journal AAD binds the authenticated expectation. The journal cannot prove a caller's claim that a source commitment belongs to those bytes if the trusted caller supplies a false pairing.

`persist(expected, bytes)` writes encrypted bytes and returns only counts, a journal-keyed commitment, and the two false completion flags. Then separately call `read(expected)` (ideally through a freshly opened journal using the independently retained expectation and keys); it returns `{bytes, summary}`. Verify the summary commitment against the persisted result, then use **only those recovered bytes** for subsequent independently authorized private preflight/append. `verify(expected)` performs authenticated readback and returns only the integrity summary, without exposing recovered bytes. It does not authorize append or perform a durability barrier. `read` returns private data intentionally to the trusted workflow; never log it or return it to untrusted callers. There is no automatic append and no production permission. Empty transaction stages, including core `transaction:null`, are valid.

## Publication, recovery and limits

Disk files contain only a random 12-byte nonce, 16-byte AES-256-GCM tag and ciphertext. Version, authenticated scope, opaque ID, stage kind, source commitment and expected digest are authenticated AAD. The entire exact stage is encrypted, including core profile data; no plaintext stage or SQL row is written. Filenames, file lengths, file counts, access timing and encrypted orphan existence remain observable. The integrity summary exposes only transaction/operation counts, a domain-bound keyed commitment and false status flags. Errors are generic, with no decrypted content, paths or attached causes.

The implementation is synchronous, Linux-only and requires `/proc/self/fd` plus working local-filesystem hard links and file/directory fsync. It opens and pins the journal directory, uses descriptor-relative proc paths and `O_NOFOLLOW`, checks owner/type/exact mode, rejects symlink path components and files, and checks the original directory inode before and after operations. Replacing the directory during publication cannot redirect the encrypted write into the replacement directory. Other platforms and unavailable fsync fail closed; no weaker fallback is advertised. No native macOS acceptance is claimed.

Publication is: exclusive random 0600 temporary file; write complete ciphertext; fsync file; atomic **hard link with no replacement** to `<id>.stage`; fsync directory; authenticated exact readback; unlink temporary name; fsync directory again. Ordinary rename is deliberately absent because Node's rename may replace an existing ID. This hard link is the publication point corresponding to a rename crash boundary. An existing ID is accepted only after authenticated readback under the same expectation and exact byte equality. Canonically equivalent API-key JSON with different bytes still conflicts. Competing writers cannot overwrite the winner. An existing malformed, truncated or wrong-key entry is never repaired, deleted or replaced.

A failure is ambiguous: publication may already have occurred. Keep the exact candidate bytes and external proof/keys; retry `persist` to authenticate/read back an existing entry and repeat directory fsync. `read` alone verifies integrity, **not** a previously failed durability barrier. Never regenerate a randomized stage after an ambiguous append or journal failure. A process death after publication can leave both final entry and encrypted temporary hard link; recovery reads the final entry, not the temporary name. A death before publication can leave only an encrypted orphan: this API deliberately does not discover, promote or delete orphans. If final entry is absent and original candidate bytes are unavailable, operator reconciliation is required before generating anything or appending. No automatic recovery guarantee is claimed for that case.

A successful return means the required fsync calls and authenticated readback completed on this filesystem. It is not proof of power-loss survival on dishonest/unsupported storage, physical backup, disk-loss recovery, distributed linearizability, immutable storage or key retention. Process-exit and injected-fault tests do not simulate hardware power loss. The pre-existing directory and its parent must themselves have been durably provisioned. The helper cannot defend against privileged processes, a malicious same-UID writer, arbitrary mount manipulation, deletion/rollback of an entire journal, or a swap away and back between inode checks. Owner-only access and trusted ancestor management are required. Separately protected expected proofs/commitments and backups are necessary to detect rollback; the API supplies no monotonic counter or external checkpoint. It cannot make journal persistence and Git append one atomic transaction or enforce caller ordering. Stage write-once behavior is an API no-overwrite guarantee under these assumptions, not a filesystem WORM claim.
