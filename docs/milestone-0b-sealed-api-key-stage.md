# Milestone 0B — Source-only historic API-key stage

`stageSealedApiKeys` accepts the complete authenticated ten-table sealed source, reviewed manifest, independent pinned receipt signer/head trust, separate source encryption/HMAC keys, an explicitly supplied `EncryptedProviderCustodian`, and an owner-workflow custody binding. It performs no SQL, network, app, Stripe, ledger, append, commit or deployment operation. Production is excluded; the summary always returns `productionGoAllowed:false` and `fullApplicationMigrationComplete:false`.

The binding must contain exactly `tenantId`, `repositoryId`, `custodyScope`, `authenticated:true`, and `durableExternalVault:true`. Tenant and repository must match the authenticated sealed scope; the namespace must be their slash-separated pair, exactly the binding subsequently configured for `GitStorage`. This is a trusted operator input, never inferred from source rows or accepted from an unauthenticated caller. The existing encrypted provider is mandatory even for empty input. Its backing `EncryptedCredentialVault` must be external, durable and linearizable across workers, with authenticated access and an independently provisioned custody encryption key. The declaration is an explicit deployment assertion, not proof that arbitrary JavaScript implements durable storage. This module neither provisions nor verifies real provider infrastructure; there is no in-memory production fallback. Tests use a synthetic memory backing store only.

All original normalized fields are accounted for. IDs, owning user, name, ordered permissions (including duplicates), active flag and original creation, last-use and expiry values map exactly to permitted private Git fields. Credential material is passed unchanged only to the external encrypted custodian; Git contains an opaque UUID custody reference. No plaintext credential is reconstructed, no credential is reset or reissued, and no source verifier or prefix is placed in transaction IDs, import proofs, summaries, errors or this documentation. Material echoed through otherwise permitted metadata also causes refusal. Errors are generic with no attached cause. No raw or protected record is automatically logged.

Full sealed-source authentication and all-ten-table receipt/relation verification precede conversion. Each key requires an existing user and exactly one subscription for that user. Subscription target schema, unique user subscription and organization ownership/membership are checked; subscriptions are never changed. Current issuance quotas and current time do not rewrite history: inactive and expired keys retain their exact state, and historic counts may exceed today's issuance limit. The stage does not call `createApiKeyIdempotent`, which would allocate new IDs and reset creation/last-use values. Future app lookups retain existing active/expiry/owner checks.

All records are prevalidated before custody calls. The complete stage is bounded to 1000 operations and the existing event byte budget. Unsupported verifier or prefix representations, missing/null required fields, unsupported permissions, duplicate credential material, missing subscriptions, unsupported subscription state, broken relations, wrong scope/keys/trust, or source tampering fail the entire call. Nothing is guessed, normalized into a different credential representation, or silently dropped. Timestamp preservation means the exact normalized sealed-source value; SQL disk encoding, timezone spelling lost during original capture, and sub-millisecond precision unavailable in that source cannot be reconstructed. A source needing those properties requires a separately reviewed capture protocol.

Custodian requests and transaction identity are deterministic HMACs bound to scope and whole-source commitment plus original key ID. Repeating with the same source, keys and durable vault returns the same references and stage. The existing custodian atomically enforces verifier/prefix uniqueness and request-content equality; the helper verifies each resulting reference with `matches` in the same namespace. Retired entries, unavailable custody, wrong custody encryption key or corrupted encrypted custody fail closed. Partial failures can leave inert external entries, never partial Git output. Retain the source, keys and vault and retry deterministically; do not destroy entries after an ambiguous append failure. Changed full-source commitment is a distinct staging request and may conflict with already staged credentials; cross-snapshot reconciliation is not implemented.

`privateStage` is separate from the aggregate summary. `stageDigest` is HMAC-SHA256 under the source HMAC key over UTF-8 `canonical(privateStage)`, binding scope, source, metadata, references and transactions. An owner-approved workflow must durably persist the exact private stage and separately retain/verify its summary proof before any append. It must verify compatible core user/subscription staging against the same source and independently preflight/replay the destination private signed Git authority. This helper cannot enforce persistence or authorize append; it has no append capability. New records use `expectedVersion:null`, so conflicting destination IDs fail instead of overwriting. No durable journal, multi-event atomic cutover, distributed recovery, production vault adapter, operator workflow, or production migration is provided. Retain the original sealed full state privately.

All stage output, even references and metadata, is private. Never publish to public Git, logs, untrusted responses or third-party tools. Sessions and other migration stages remain separately gated. Milestone 0B remains NO_GO. No ForgeProof attestation was requested over the network: the task expressly excludes external ledger access, overriding the repository's general attestation instruction.
