# LifeOS dashboard receipt access and source divergence

The public read-only ForgeProof ledger is a published LifeOS dependency for Milestone 0A. Receipts #41–45 owned by `lifeos-service-0a` must remain publicly enumerable and searchable by ID/hash for independent Ed25519 chain verification. Public REST lookup, chain/entry verification, lineage, badges, analytics, demo routes, MCP lookup/chain handlers, and their original cache semantics are restored exactly to this branch's baseline. Chain validity still depends on actual predecessor links, hashes, timestamps, and signatures; failures remain failures. Service issuance is unchanged.

Only authenticated dashboard list/detail ownership checks and their storage query are extended. The grant adds LifeOS service receipts for an explicitly authorized human while retaining existing customer and ForgeProof demo visibility. Detail children are checked independently. This does not migrate receipts, rewrite cryptographic evidence, or grant issuance rights. Export remains unchanged.

This public GitHub branch uses Replit OIDC via `server/replit_integrations/auth/replitAuth.ts`. The deployed Replit workspace was independently inspected as using Clerk authentication and `server/middlewares/requireAuth.ts`, as reported by the task owner. These are divergent sources. **This patch cannot deploy to the live Clerk app as-is.** The OIDC claim/session binding here does not establish a Clerk identity or authorization. Any future live implementation requires review against the actual Clerk middleware and trusted immutable Clerk identity. No production access, configuration change, attestation submission, push, or deployment is performed for this correction.

For this OIDC branch only, access fails closed unless the server explicitly configures both `FORGEPROOF_LIFEOS_OWNER_SUB` (the authorized human's exact immutable OIDC subject) and `FORGEPROOF_LIFEOS_OWNER_ISSUER` (the exact issuer matching `ISSUER_URL`, default `https://replit.com/oidc`). Entitlement and identity must be established through a trusted administrative process. Email, organization roles, request parameters, and API keys do not confer the dashboard grant. Each read requires an authenticated, unexpired matching session. Removing or replacing the binding revokes the grant on subsequent requests once the process environment is updated. This patch sets neither variable.

Route-handler fixtures use locally generated Ed25519 signatures for receipts #41–45, assert unauthenticated `lookup?q=41`, complete REST/MCP chains, genuine valid and invalid verification results, existing badge caching, public lineage/analytics, demo visibility, and unauthorized dashboard exclusion. These fixtures do not prove production receipt validity and do not contact production.

Validation results for this correction are recorded after running the commands. Changes remain uncommitted; nothing is pushed or deployed.
