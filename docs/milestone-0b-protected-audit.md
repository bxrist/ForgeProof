# ForgeProof Milestone 0B — protected historical audit metadata

This nonproduction-only extension handles historical `audit_logs` rows whose `metadata` is non-null. A dedicated private Git event contains a **signed event** whose body includes a redacted, validated audit core and AES-256-GCM authenticated ciphertext containing the complete original exported JSON bytes. The ciphertext is authenticated using a runtime-injected 32-byte key, a fresh nonce, and AAD scoped to tenant, repository, audit ID and core digest. Keys are never committed to Git or serialized in event records.

**Trust distinction:** Existing audit logs are **not individually Ed25519-signed**; their source-of-record evidence depends on independent verification of the consistent SQL export and the new authenticated Git event. Keyless replay validates the protected envelope/ciphertext checksum and signed Git event integrity but cannot decrypt or independently prove the original SQL metadata without the external key. Authorized decrypt verifies the authenticated tag, ciphertext and original-byte hash, and compares all redacted nonsecret fields before returning exact bytes. If the external key is lost, exact private audit restore fails closed.

The `GitStorage` read model uses validated redacted audit cores for API-facing audit queries and never returns protected ciphertext or metadata through those legacy `IStorage` methods. The same adapter recognizes protected receipt cores and exposes only their signed redacted fields. Existing v1 rows and synthetic upstream tests remain supported.

Native synthetic tests cover signed Git replay, private bare repository clone, original-byte recovery, idempotency, provider-independent read model, wrong-key and wrong-tenant negatives, malformed envelopes, and ciphertext tamper. These tests do **not** attest production migration, secret custody durability, authenticated user sessions, Stripe lifecycle continuity or disaster recovery from actual production records.

**Production export caveat:** The historical PostgreSQL schema stores receipt fields and their signatures, but not necessarily the original bytes of the user-facing issuance response. A reproducible, reviewed SQL export can preserve its own exact serialized snapshot bytes, field values and cryptographic signatures; it cannot claim to reconstruct issuance bytes that were never stored. Historical source timestamps, receipt IDs, public signer keys and global predecessor links must be preserved without inventing attribution.

**Still required for 0B GO:** A single consistent read-only production snapshot with independently reconciled counts and key pins; user/API key/session custody and reauthentication; private encrypted migration of actual receipt and audit metadata; a production-ready Git-authoritative service with existing UI, auth, billing and API semantics; durable Git checkpoints, tested backup/failover and independent Darwin acceptance. Do not connect this experimental branch to production or write confidential data into the public product source repository.
